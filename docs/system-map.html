Supplier Agent System Map

The product finds the cheapest way for a small business to restock its supplies. It reads past bills, searches real supplier sites in parallel, texts and calls the current distributor, and brings the owner to a ready checkout. Code makes sure that no agent can submit a payment.

Designed, not built v2: review fixes folded in Name: chosen at H0 Demo business: Hearthloaf Bakeries (company-001)

1. User flow, end to end

The owner sees five screens and acts three times: start the comparison, approve a plan, and later place the order. The backend work under each screen runs while that screen is open.

2. Agent orchestration on a timeline

Each supplier gets its own lane with one browser session. The lanes run in parallel and report independently, so the optimizer improves the plan with each report. The distributor call starts as soon as a plan exists, without waiting for the other lanes. At the deadline, the results use whatever has finished.

3. Technical architecture

One Python backend holds all the state, the plain-code stages, the Jev client and the payment rules. The supplier lanes and the phone service are workers that report events back. Only the webhook routes are open to the internet, through a tunnel.

4. Restock planner and feedback loop

The planner decides when to order and how much. The sourcing pipeline decides where. Code makes every number. Jev only names the cause of a forecast miss (J11) and reads owner messages (J12), and code applies a fixed rule for each answer.

5. Jev decision points

Jev answers narrow questions with calibrated probabilities. Code finds the candidates, Jev chooses among them, and code acts on the answer. Jev never does arithmetic, writes text or reads images.

6. Reliability

The system fails closed on safety and degrades on everything else. A failure removes one supplier, one channel or one decision. The job still ends with labelled results.
